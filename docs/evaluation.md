# Evaluation methodology

> This page covers **retrieval and answering (Phases 1–2)**. Document-intelligence evaluation (Phase 3: extraction, OCR, tables, validation, review, multi-document queries, security matrix) is described in [extraction-evaluation.md](extraction-evaluation.md), with generated results in [extraction-evaluation-results.md](extraction-evaluation-results.md). The Phase 3 work did not change the frozen Phase 2 dataset or its results.

NEXUS AI's retrieval, abstention, citation and authorization behaviour is measured by `scripts/evaluate.py` against a frozen, hand-labeled dataset. The script uses real PostgreSQL, persisted `multilingual-e5-small` embeddings, the production retrieval code and the production `/api/ask` endpoint. Every number in [benchmark-results.md](benchmark-results.md) and in the README benchmark section is generated by that script. A unit test fails if either file differs from a fresh render of `eval/reports/latest.json`.

```mermaid
flowchart LR
  Q[eval/questions.jsonl<br/>question + verbatim evidence quotes] --> B[build_eval_dataset.py<br/>production chunker]
  C[eval/corpus/*.txt + manifest.json<br/>30 docs, 2 tenants, ACL] --> B
  B --> F[eval/retrieval.jsonl<br/>frozen chunk-level labels, dev/test split]
  F --> E[scripts/evaluate.py]
  C --> DB[(nexus_eval<br/>migrated · seeded · embedded<br/>verified row-by-row)]
  DB --> E
  E --> R1[4-mode retrieval benchmark]
  E --> R2[RRF ablation<br/>select on dev → report test]
  E --> R3[evidence-policy calibration<br/>select on dev → report test]
  E --> R4[/api/ask end-to-end<br/>citations · facts · abstention]
  E --> R5[security oracle<br/>candidates · sources · citations · prompts]
  R1 & R2 & R3 & R4 & R5 --> OUT[eval/reports/latest.json · latest.md<br/>docs/benchmark-results.md · README]
```

## Corpus

- **30 fictional documents → 59 chunks**, produced by the same chunker the app uses on upload (1,000 characters, 150-character overlap). Chunk IDs are stable and readable: `<document id>:p<page>:c<position>`.
- **Two tenants** (Northstar with 25 documents, Otherco with 5) and **six access groups**. One NDA is owned by the IT persona but granted only to Legal, which exercises the owner rule.
- **Languages:** 21 English and 9 Croatian documents.
- **Deliberate distractors:**
  - Atlas *Industrial* vs Atlas *Logistics*.
  - Nearly identical IDs: `NS-SUP-2026-041`, `NS-SUP-2026-014`, `OC-SUP-2026-041`, `NS-SUP-2026-041-A1`.
  - A contract and its amendment with conflicting notice periods (90 → 60 days) and contract values.
  - Helix vs Helios.
  - The same leave policy and Cygnus SLA in two tenants with different numbers (20 vs 22 days, 99.9 vs 99.5 %).
- **Authorized chunks per persona:** finance 35, HR 12, IT 20, admin 51, Otherco 8.

## Ground truth

`eval/questions.jsonl` has **100 questions** across 10 categories: exact identifier, keyword, paraphrase, Croatian, cross-language, numeric/date, multi-document, distractor, unanswerable and authorization. It contains 82 answerable questions, 10 that are unanswerable from the corpus, and 8 whose only answer lies in a document the persona may not read.

- **Labels come from documents, never from retrieval output.** Each question lists verbatim *evidence quotes* with a grade: 2 for primary evidence, 1 for supporting evidence (for example the superseded original clause next to its amendment). `scripts/build_eval_dataset.py` marks a chunk relevant if it contains a quote. A quote that appears in two chunks because of overlap makes both chunks relevant.
- **Authorization is labeled separately.** Evidence in a document the persona cannot read goes to `unauthorized_relevant_chunk_ids` and is **never** counted as relevant. Such cases are scored by abstention and security checks, not by recall.
- **Validation is strict.** The build fails if a quote is not found verbatim, if an answerable question cites unreadable evidence, if an unanswerable question has authorized evidence, if an expected fact is missing from the relevant chunks, on duplicate IDs, or on an unknown category, persona or document. `load_frozen` also fails if `eval/retrieval.jsonl` differs byte-for-byte from a fresh rebuild. Both checks run in CI (`test_eval_dataset.py`).
- **Split.** The split is deterministic and stratified: within each category, ordered by ID, questions alternate dev/test. That gives 50 dev and 50 test questions (41 answerable in each) with no overlap.

## Metrics (chunk level, macro-averaged over answerable questions)

| Metric | Definition |
|---|---|
| Recall@k | \|relevant ∩ top-k\| / \|relevant\| |
| Precision@5 | \|relevant ∩ top-5\| / 5 (divides by 5 even when fewer results are returned) |
| Hit Rate@5 | 1 if any relevant chunk is in the top 5 |
| MRR@10 | 1 / rank of the first relevant chunk within the top 10, otherwise 0 |
| nDCG@5 | DCG@5 / IDCG@5 with gain 2^grade − 1 and discount log2(i + 1) |

These metrics are **undefined** for questions without authorized relevant chunks. Such questions are excluded explicitly (the code raises `UndefinedMetric`) instead of being scored 0 or 1. Recall@1 is mathematically capped below 1 for questions with more than one relevant chunk. Confidence intervals come from a percentile bootstrap over questions (2,000 resamples, seed 0). Mode differences use a *paired* bootstrap on the same questions.

**Latency** is measured as warm per-query wall time and broken down into embedding, semantic DB, FTS and fusion time (p50 and p95). The cold-start figure is model load plus the first query in a fresh process. Latency is machine-dependent: two runs on the same laptop gave hybrid p50 values of 26 ms and 43 ms. It is reported but never gated.

## Results and analysis

Results as of the report in `eval/reports/latest.json` (dataset sha256 `1a3c160c9645e075…`; exact values in benchmark-results.md):

- **No mode is significantly better on the held-out test split.** All four strategies land at nDCG@5 ≈ 0.70–0.74, and every paired hybrid-vs-X confidence interval contains 0. Semantic has the best Recall@5 and Recall@10 (it ranks *something* relevant in a long list), while FTS has the best precision at the very top. On all 82 answerable questions, hybrid has the highest nDCG@5 (0.761 vs 0.726–0.728), but with n = 41 per split this does not survive the test split. **"Hybrid wins" is not claimed.**
- **Cross-language is the weakest category for every mode.** nDCG@5 is 0.00 (BM25), 0.12 (FTS), 0.34 (semantic) and 0.28 (hybrid). Lexical methods cannot cross languages at all. Per-case inspection shows that e5-small has a **same-language bias**: for a Croatian question about an English document, the top 3 semantic results are usually Croatian documents (q042, q044, q045), and the reverse also happens. Hybrid inherits the lexical branch's same-language matches and loses part of the semantic gain. A stronger cross-language embedder was evaluated in Phase 2d and not adopted (see [Embedding model comparison](#embedding-model-comparison-phase-2d-dev-split-only)).
- **Distractors hurt semantic most** (0.55 vs FTS 0.75). Embeddings of "Atlas Industrial" and "Atlas Logistics", or of the two Cygnus SLAs, are nearly identical, while exact tokens tell them apart.
- **Exact identifiers favour hybrid** (0.91), as the design intends: FTS pins the identifier and semantic adds context.
- **Chunk size.** With 1,000-character chunks, most documents split into only 2 chunks, so top-10 lists cover a large share of a small persona's corpus (Otherco has 8 chunks, so metrics there saturate at 1.0). Smaller chunks would make ranking harder and more informative. That is a corpus/ingestion change, not done here.

## Hybrid RRF ablation (dev → test)

The grid has 80 configurations: weights {1:1, 1:2, 2:1, 1:3, 3:1} × candidates {10, 20, 50, 100} × k {10, 30, 60, 100}. Selection is by dev nDCG@5 only. The best dev configuration (10 candidates, k = 30, lexical weight 3) improved dev nDCG@5 from 0.788 to 0.805, but on test it changed nDCG@5 by **+0.0045** and Recall@5 by **−0.012**, which is noise at n = 41. **The default (50 candidates, k = 60, equal weights) was kept.** The values of k barely matter at these candidate depths, and the top dev configurations differ only in weights and candidates.

## Evidence sufficiency (abstention)

The policy (`backend/app/evidence.py`, shared by the API and the calibration code) runs after permission-scoped retrieval and before citations and prompt construction:

1. **Identifier rule.** If the question contains identifiers (letters + `-` + digit, e.g. `NS-SUP-2026-041`, `KESTREL-9`), **all** of them must occur as exact tokens in an authorized candidate. Otherwise the answer is `no_evidence` (`identifier_not_found`). If they all occur, the question is answered.
2. **Similarity rules**, OR-ed, each disabled when set to `none` (skipped, not a threshold of 0): best *chunk* cosine of the semantic branch; best *sentence* cosine among the query-selected sentences of the top 3 hits (Phase 2d); share of question content terms covered by a top hit; optional branch agreement.

Calibration sweeps 1,295 candidate policies per mode across five families (`chunk`, `sentence`, `chunk_or_sentence`, `chunk_or_coverage`, `sentence_or_coverage`). It selects by **dev** balanced accuracy (tie-break: fewer false abstentions, simpler family, higher thresholds) and reports the result on test. **Selected on dev for semantic and hybrid: `sentence`, identifier rule + sentence cosine ≥ 0.835, chunk rule off.** It is the API default, and tests fail if `config.py`, `main.EVIDENCE_POLICY` or `.env.example` drift from `eval/calibration.json`.

Hybrid confusion matrices (positive = the system answers; "harmful FN" = abstained although a relevant chunk was in the top 5):

| Policy | split | TP | FN | FP | TN | answerable recall | unanswerable detection | balanced acc. | harmful FN |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Phase 2c, chunk cos ≥ 0.82 | dev | 36 | 5 | 2 | 7 | 0.878 | 0.778 | 0.828 | 2 |
| Phase 2c, chunk cos ≥ 0.82 | test | 35 | 6 | 2 | 7 | 0.854 | 0.778 | 0.816 | 3 |
| **Phase 2d, sentence cos ≥ 0.835** | dev | 35 | 6 | 1 | 8 | 0.854 | 0.889 | 0.871 | 3 |
| **Phase 2d, sentence cos ≥ 0.835** | test | 33 | 8 | 0 | 9 | 0.805 | **1.000** | 0.902 | 4 |

**The trade-off, stated plainly.** On the held-out test split the Phase 2d policy refuses **every** unanswerable question (9/9, up from 7/9), but it also refuses **2 more answerable questions** (8 false abstentions instead of 6, false-abstention rate 0.195 instead of 0.146). Only one of the extra refusals is harmful in the strict sense (4 instead of 3 abstentions where the evidence was in the top 5). The other false abstentions follow a retrieval miss, where the system had no relevant chunk to quote anyway. Phase 2d therefore did **not** reduce false abstentions overall. It moved the operating point towards "abstain rather than guess", which is the design invariant, and it was chosen on dev without looking at test. With 9 unanswerable questions per split, one question is 0.111 of unanswerable detection, so the gain is two questions and not a precise estimate.

Findings:

- **Sentence similarity separates answerable from unanswerable a little better than chunk similarity.** On dev (hybrid), the answerable median is 0.868 and the unanswerable median is 0.827 for sentences, against 0.847 / 0.819 for chunks. The ranges still overlap (unanswerable maximum 0.863), so no threshold is clean.
- **Cross-language false abstentions did not change** (test: 2 of 6 cross-language questions refused under both policies). The extra refusals are English questions (test, en: recall 0.742).
- **The Croatian Atlas demo question**, which was the documented Phase 2c false abstention (chunk cosine 0.810 < 0.82), is now answered. Its best sentence (*"…at least 90 days before the current end date."*) reaches 0.857 against the English clause, above 0.835. `backend/tests/test_answers_pg.py` checks this end to end on PostgreSQL with the real model and the real demo documents, together with the same question for personas without access and a question with no evidence. Nothing in the code is specific to this question.
- **The identifier rule does most of the work** for authorization questions: a forbidden or non-existent identifier is never found in authorized text.
- Branch agreement and term coverage were evaluated and not enabled.

## Answers and citations (end-to-end `/api/ask`)

### Query-aware offline extraction (Phase 2d)

Without an LLM key, the answer quotes the best 2 sentences of each of the top 3 authorized hits **verbatim**, with one `[S#]` per quote. Sentences are scored by `1.0 · e5 cosine + 0.5 · share of question terms`. The configuration was selected on dev from 22 configurations (`runner.extraction_study`, retrieval fixed to hybrid top-5 with the policy **off**, which isolates the extractor):

| Extractor | dev (n = 37) | test (n = 39) | test, given the fact was retrieved |
|---|---:|---:|---:|
| Phase 2c: first 330 characters of each source | 0.189 | 0.333 | 0.406 |
| **Phase 2d: query-aware sentences** | 0.595 | **0.590** | 0.719 |

Mean answer length dropped from about 1,114 to 919 characters, and there were 0 non-verbatim quotes.

### End to end, with the evidence policy

Every question is sent through `/api/ask` in every mode, with the shipped policy, `top_k = 5` and no LLM key. All 100 questions are used in the full run (`latest.json`), and the 50 test questions in the CI run (`ci.json`).

- **Citation integrity:** every `[S#]` must resolve to a returned source, every source's `document_id`, `page` and excerpt must equal the stored chunk, and every quoted line must be a substring of the chunk it cites. Result: 100 % valid, 0 mapping errors, 0 non-verbatim quotes, 0 unauthorized citations.
- **Answer fact recall** (all expected facts in the answer text; abstentions count as misses):

  | Mode | Phase 2c, all 100 | Phase 2d, all 100 | Phase 2c, test (CI) | Phase 2d, test (CI) |
  |---|---:|---:|---:|---:|
  | BM25 | 0.237 | 0.579 | 0.282 | 0.615 |
  | FTS | 0.250 | 0.566 | 0.308 | 0.564 |
  | Semantic | 0.250 | 0.579 | 0.308 | 0.590 |
  | Hybrid | 0.250 | 0.566 | 0.308 | **0.538** |

  Hybrid end-to-end on test (0.538) is lower than the isolated extractor (0.590), because the policy now refuses 8 answerable test questions. This is the cost of the abstention trade-off above. CI gates this exact metric (`hybrid_min_answer_fact_recall` = 0.48 in `eval/ci_thresholds.json`), and the Phase 2c extractor (0.308) would fail it.
- **Unsupported fact answers** (a fact in the answer but in no cited chunk): 0 in every mode.
- **LLM answers are not evaluated** (no API key in this environment). The pipeline is ready (`rag.answer`), and an LLM run would be scored by the same deterministic fact and citation checks. No LLM judge is used anywhere.

## Embedding model comparison (Phase 2d, dev split only)

`scripts/compare_embedders.py` re-indexes the same corpus with the same chunker into a separate disposable database for each model and runs the dev split through the production semantic and hybrid code. Results are in `eval/reports/embedders-dev.json` (41 answerable dev questions). The test split was **not** used.

| Dev, nDCG@5 | `intfloat/multilingual-e5-small` (current) | `paraphrase-multilingual-MiniLM-L12-v2` |
|---|---:|---:|
| Semantic, all answerable | **0.719** | 0.530 |
| Semantic, cross_language (n = 6) | 0.415 | **0.794** |
| Semantic, exact_identifier (n = 5) | **0.800** | 0.100 |
| Semantic, croatian (n = 5) | **0.926** | 0.526 |
| Semantic, distractor (n = 5) | 0.486 | 0.477 |
| Hybrid, all answerable | **0.788** | 0.688 |
| Hybrid, cross_language | 0.306 | **0.447** |
| Hybrid, exact_identifier | **0.886** | 0.586 |
| Semantic Recall@5, all | **0.805** | 0.646 |

| Cost | e5-small | MiniLM-L12 |
|---|---:|---:|
| Parameters / fp32 weights | 117.7 M / 448.8 MB | 117.7 M / 448.8 MB (same 12-layer, 384-d multilingual MiniLM backbone) |
| Embedding dimension | 384 | 384 (fits `vector(384)`; no migration) |
| Corpus indexing (59 chunks, CPU) | 15.8 s | 6.1 s |
| Model load (process cold start) | 39 s | 98 s (single measurement; not investigated, may include a first-time download) |
| Warm query wall time p50, semantic / hybrid | 90 / 108 ms | 82 / 87 ms |
| Prefixes | `query:` / `passage:` | none (`NO_PREFIX_MODELS`) |
| Authorization leaks | 0 | 0 |

**Decision: e5-small is kept.** MiniLM nearly doubles cross-language semantic nDCG@5. On the other hand, overall semantic quality drops by 0.19, exact-identifier retrieval collapses (0.80 → 0.10), same-language Croatian drops by 0.40, and hybrid overall drops by 0.10. Cross-language is 6 dev questions, while the losses hit every other category. Switching models would also require re-embedding every chunk (the stored `model_name` / `model_revision` would change) and recalibrating the evidence policy, whose cosine thresholds are model-specific. The test split was not run for MiniLM, because nothing was adopted.

## Query translation experiment (Phase 2d, not adopted)

**Failure analysis first** (dev, semantic, the 6 cross-language questions, `eval/reports/latest-cases.jsonl`). In 4 of 6 cases the relevant chunk is retrieved but ranked 2nd to 4th, so the main problem is ranking, not a complete miss. Pure same-language bias shows in 2 cases: q043 and q045 return mostly Croatian documents for a Croatian question whose answer is in an English document, and for q045 the relevant chunk is not in the top 10 at all. q041 is a topic confusion inside the right language: an English legal document, but the wrong one.

**Method.** `scripts/experiment_query_translation.py` (optional extra `mt`, not part of the API or the Docker image) translates each question into the other corpus language with local MarianMT models: `Helsinki-NLP/opus-mt-sla-en` @ `90572be0` and `opus-mt-en-sla` @ `0bc26914` (target `>>hrv<<`), 2 × 75 M parameters, 571 MB fp32. The translation is searched as an **additional** permission-scoped branch (production `semantic_search` / `fts_search`) and fused with the production RRF. The original query's branches are always kept, so identifiers and intent are never replaced. The direction comes from a small deterministic HR/EN detector, which was 100 % accurate on both splits; dataset labels are only used to report that accuracy. Translation preserved every identifier (9/9 dev, 7/7 test). Baseline variants reproduce the production numbers exactly.

**Adoption rule, fixed before measuring:** dev cross-language nDCG@5 must improve by ≥ 0.10, dev overall nDCG@5 must drop by ≤ 0.01, with zero leaks. Only the dev-best passing variant per mode is then run once on test.

| nDCG@5 (n = 41 answerable) | dev overall | dev cross-lang (6) | **test overall** | **test cross-lang (6)** | test distractor | test exact id | test croatian | test Recall@5 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| semantic (production) | 0.719 | 0.415 | 0.737 | 0.272 | 0.618 | 0.926 | 0.926 | 0.850 |
| semantic + translated query | 0.725 | 0.760 | **0.648** | 0.470 | 0.585 | 0.649 | 0.809 | 0.813 |
| hybrid (production) | 0.788 | 0.306 | 0.734 | 0.250 | 0.688 | 0.926 | 0.926 | 0.809 |
| hybrid + translated (FTS + semantic) | 0.813 | 0.689 | **0.721** | **0.760** | 0.540 | 0.853 | 0.830 | 0.894 |

`hybrid + translated semantic only` passed on dev too (0.781 / 0.432), but it was dominated by the variant above and was not run on test. All variants had 0 authorization leaks.

**Result: not adopted.** The cross-language gain is large and does repeat on test: hybrid cross-language nDCG@5 rises from 0.25 to 0.76, and Recall@5 overall from 0.809 to 0.894. **The overall gain does not repeat.** On test, overall nDCG@5 falls by 0.013 (hybrid) and 0.089 (semantic). The translated branch also pulls other-language documents into **same-language** questions: Croatian falls from 0.93 to 0.83, and distractor and exact-identifier quality fall as well. Translation adds 426 / 521 ms p50 per query (dev / test, CPU), roughly 10× the retrieval time, plus 571 MB of model weights. Both cross-language subsets have only 6 questions, so their gains carry wide uncertainty.

**What would be worth trying next:** gating the translated branch, e.g. a lower RRF weight, or using it only when the original branches' best sentence similarity is low. That is a new hypothesis and needs a fresh dev round, with the test split used once. A larger multilingual embedder (a different dimension, so a schema migration) is the other option.

## Reproduce

```bash
docker compose up -d db
python scripts/build_eval_dataset.py     # only after editing questions/corpus; validates labels
python scripts/evaluate.py               # full run (~10 min CPU): reports, docs, README, calibration
python scripts/compare_embedders.py      # embedder comparison on the dev split (separate *_eval database)
python scripts/evaluate.py --ci          # CI gate (~4.5 min): test split, no ablation, thresholds in eval/ci_thresholds.json
```

Set `EVAL_DATABASE_URL` to use a different server. The database name must end in `_eval` or `_test`, because it is dropped and re-created on every run.

## Limitations

- The corpus is synthetic and small, and the questions were written by the same author as the documents, so there is a risk of lexical-overlap bias. Absolute numbers will not transfer to real document collections. The *methodology* and the *relative* findings (language bias, distractor sensitivity, weak cosine signal) are the deliverable.
- With 41 answerable test questions, differences below about 0.05–0.08 nDCG@5 are not resolvable (see the CIs).
- The abstention threshold is calibrated on 9 unanswerable dev questions. Treat it as a starting point and recalibrate on real traffic.
- Only one embedding model was evaluated. Multilingual alternatives (larger e5 models, bge-m3) or query translation are the obvious next experiments for the cross-language gap.
